# Phase 0 研究：姿态残留轮廓的定位与修法取舍

**Feature**: 001-fix-ghost-outline | **Date**: 2026-11-24

本文件把规格里的未知项逐条收敛成决策。每条包含：决策、依据、被否方案。

---

## R1 · 残留的物理成因

**决策**：残留是"**深度有内容、颜色为空**"的像素被合成阶段的描边/凹陷项消费所致；具体到跨帧为何保留，按"深度附件累积（A）"为首要假设推进，并以审计产物为裁决依据，而非先入为主。

**依据**：

1. 像素级证据（用户截图测量）：线宽 1–2 px；轮廓内部与背景差 ≈ 0（±2）；线条比背景暗 5–10 级。三个特征同时成立，只可能是"压暗型边缘效果"作用在一个"只有几何存在性、没有颜色"的信号上。
2. 渲染器把描边完全建立在深度上：合成着色器取深度四邻做拉普拉斯，判据是"该像素有没有几何"（`step(dc, 1-ε)`），**不判断"有没有颜色"**。
3. 背景（天空/地面）在合成阶段按相机基向量程序化生成，不写入场景颜色附件。这解释了为什么残留表现为"线框"而不是"整块旧画面"：颜色缓冲区被清空后，任何残留的深度都只能通过描边项留下一条线。
4. 已排除的替代解释：白色材质与天空同色（内部残差为 0，实体面应有 ~20 级差）；镜像地板（`floor_reflectance` 默认 0，核心层未设置）；外部场景物体（外部物体存在时网格地面不绘制，而现场有网格）。

**被否方案**：把残留解释为"某 link 变换滞后一帧"。运动学每帧全量重算，无增量缓存；且网格材质不透明、单次绘制必然同时写颜色，无法产生"只写深度"的结果。

**仍待裁决的部分**：A（附件跨帧累积）与 B（同帧二次深度写入）。裁决不看推测，看审计输出的**簇形状**：残留像素簇若与世界空间中**历史姿态**重合 → A；若与当前姿态重合 → B。两种情况下主修都成立（见 R2）。

## R2 · 修复层次

**决策**：**主修 = 合成阶段颜色覆盖门控**；**次修（条件启用）= 3D pass 的附件生命周期修复**。

**依据**：

- 门控直接表达规格 FR-005 的语义："没画过颜色的地方不允许出现轮廓"。它与根因解耦：无论 A 还是 B，甚至未来出现第三种"深度残留"来源，该像素都不会被描边。
- 代价是一次比较 + 一次乘法，位于已经逐像素执行的合成着色器内，不新增通道、不新增回读、不改变几何绘制次数。
- 次修只在审计确认"跨帧累积"时启用，避免为不确定的根因引入 pass 生命周期改动（该改动风险更高：可能影响 SSAA、阴影级联与部分重绘路径）。

**被否方案**：

| 方案 | 否决理由 |
| --- | --- |
| 关闭描边/凹陷效果 | 违反 FR-007；用产品退化换安静 |
| 仅做生命周期修复 | 若根因判定错误则问题复现；且不覆盖"同帧二次写入"类残留 |
| 在调用方（core 的 `RobotViewer`）规避 | 调用方只能整块隐藏/重建视图，属掩盖症状；且会绕过所有使用该组件的界面 |
| 每帧重建整个 pass 与纹理 | 帧率与显存代价过大，违反 SC-005 |

## R3 · 覆盖阈值

**决策**：以"**覆盖 ≥ 1/4 像素**"作为参与描边的门槛（即覆盖值 > 0.25），而不是"任何大于 0 的覆盖"。

**依据**：3D pass 以 2× 超采样渲染后由合成阶段做四点平均，一个输出像素由 4 个子样本合成。真实 silhouette 的边缘像素覆盖约为 0.5；1/4 的门槛能保留抗锯齿边缘，同时把"覆盖为 0"与"极低覆盖噪声"排除。该阈值随 `SSAA_SCALE` 派生的 1/4 关系写入契约，避免硬编码魔数。

**被否方案**：门槛取 0（会被浮点噪声触发，边缘出现麻点）；门槛取 0.5（会吃掉单侧边缘，使描边断裂，违反 SC-004）。

## R4 · 验收与回归手段

**决策**：三层验证——纯逻辑单测（CI）+ 设备端读回审计（开发期）+ 人工基线截图（5 个界面）。

**依据**：

1. Makepad 提供 `Texture::read_back`，可把颜色与深度附件读回主存。于是"残留"可以被算成一个**整数**：`count(pixels where depth < 1-ε and coverage ≤ 0.25)`。这正是 FR-005 的可计数形式，避免"看着差不多"的主观验收。
2. 残留判定逻辑（阈值、计数、簇聚类）可以抽成不依赖 GPU 的纯函数，用 `cargo test` 覆盖；GPU 侧只做"读回 + 调用纯函数 + 打日志"。
3. macOS 未授予本工具屏幕录制权限，自动化截图不可用；因此读回审计是唯一能由实现者独立执行、且可重复的客观手段，人工截图仅作为最终观感确认。

**实施修正（2026-11-24）**：读回 API 只支持 `RenderBGRAu8`，深度附件不可读。原方案"直接读回颜色+深度"不成立，改为两段式采集：掩码写入 8 位目标 → 分块下采样 → 读回小目标后在 CPU 求和。语义与验收标准不变（仍是"数残留像素"），只是采集路径更长。

**被否方案**：仅靠人工目视（违反 SC-003 的 15 场景可复核性）；引入图像对比框架（新增依赖，违反约束）；把审计放进 CI（无 GPU 上下文，且 CI 为 Linux 无窗口）。

## R5 · 补丁落点

**决策**：在 `vendor/makepad-urdf-player` 就地修复，并更新 `NEXUS_PATCH.md`；上游回馈单列为后续事项。

**依据**：该目录已是经 `[patch]` 指向的本地副本（源 `283d303`），并已有补丁记录惯例（非均匀缩放、prismatic 关节等）。就地修复可立即生效、可被 CI 覆盖（workspace 内 crate），且不引入新的依赖或 fork。上游回馈需要独立的 review 流程与跨仓库验证，不应阻塞本次修复。

**被否方案**：直接改上游仓库（无法在本仓库验证）；在 `dorobot-studio-core` 里另写一份合成着色器（重复实现，且会与 viewer 的其它视觉特性分叉）。

## R6 · 性能测量

**决策**：用"审计关闭 + 连续拖动 10 秒的帧时间分布"对比修复前后，取平均值与 p95；复用 viewer 自带的 GPU 计时能力，不新增计时设施。

**依据**：规格 SC-005 只要求"与基线同档位（≤105%）"，不需要精确到亚毫秒。门控是纯 ALU 增量，理论上不可测；测量目的是排除意外（如寄存器压力上升导致着色器溢出）。

**被否方案**：帧率目视（噪声大）；引入外部 profiler（改变运行环境）。

---

## R7 · 回滚与灰度

**决策**：提供环境变量 `URDF_GHOST_GUARD=0` 关闭门控，恢复修复前行为；默认开启。该开关只影响合成阶段的一个分支，不改变其它任何视觉特性。

**依据**：现场若出现"描边变细/断裂"等主观退化，可在不重编译的情况下对照判定是门控还是别的原因；同时让"审计基线"与"修复后"能在同一二进制上并排比较，减少构建差异带来的噪声。

**被否方案**：编译期 feature flag（需要重新构建，且会把一次性开关永久留在依赖图里）；无开关直接改（出问题时只能回滚整个补丁）。

## R8 · 第二种症状（2026-11-24 现场发现）：启动即出现的高频点状噪声

**现象**：`cargo run` 默认进入 Nano 仿真，未做任何视角/关节操作，机器人周围的**地面区域**出现一圈黑白点状噪点，边界近似圆形，区域内的网格线与阴影仍在。

**为什么单列**：它与症状 A（操作后残留的历史轮廓）有三个不同点——① 无需交互即可出现；② 形态是高频点噪声，不是轮廓线；③ 边界连续、近似以机器人为中心的圆。**不能默认二者同源**。

**候选机制（按可能性）**：

| # | 机制 | 支持点 | 反证/待验 |
| --- | --- | --- | --- |
| B1 | 棋盘地面（`s5` 格）在远处欠采样产生摩尔纹/噪点 | 代码里确有 `floor`+`fract` 的棋盘（`draw.rs:475-477`），且只有距离淡出（`extent*0.75`）没有抗锯齿 | 噪点是黑白高对比，而两种土色都偏浅；需看 `URDF_SHADOW=0` 是否仍噪 |
| B2 | 阴影贴图（CSM）在覆盖范围内走样/自阴影（shadow acne） | 噪点边界近似"以机器人为中心的盒子"→ 与级联覆盖范围吻合；网格乘阴影后可呈黑白 | `URDF_SHADOW=0` 应消除 |
| B3 | 合成阶段的凹陷/描边项作用在噪声深度上 | 与症状 A 共用同一通道 | `URDF_EDGE=0` 应消除 |
| B4 | 附件未初始化（garbage alpha/depth） | 与 R1 的"A 类累积"同族 | 若 `URDF_GHOST_GUARD=0` 与 `=1` 无差别，且 `URDF_EDGE=0` 仍噪 → 更像 B1/B2 |

**判别实验（每条 1 分钟，不改代码）**：

```sh
URDF_SHADOW=0 ./target/debug/dorobot-flex   # B2 消失？
URDF_EDGE=0   ./target/debug/dorobot-flex   # B3 消失？
URDF_GHOST_GUARD=0 ./target/debug/dorobot-flex  # 与默认对比，确认当前门控与它无关
# 再把相机拉远：圆盘随之缩小/消失 → B1 或 B2（与距离/覆盖范围相关）
```

**决策规则**：若 B1/B2 成立，它属于**另一个缺陷**，应开新规格（例如 `002-ground-shadow-noise`），不并入 001——否则 001 的验收标准（残留像素 = 0）会被一个与姿态无关的现象污染。若 B3/B4 成立，则并入 001，作为同一不变量下的第二个表现。
